# Pixel-art pipeline

Why this shape: no image model or pixel-art MCP over 1k stars produces
pixel-exact, palette-true output, and Claude outputs no images at all (see
[opus-5-5.md](opus-5-5.md)). So exactness comes from a deterministic script,
and the model's job is authoring and critique.

## The flow

1. **Palette file** — one per game, from Lospec, as a hex list
   (`art_src/palettes/<name>.hex`). Index 0 is transparent.
2. **Sprite source = palette-indexed text grid** (`art_src/<sprite>.txt`):
   one character per pixel, `.` transparent, `0-9a-f` palette indices;
   frames separated by a blank line. Diffable, reviewable in git, editable by
   hand or by the model.
3. **Our renderer** (`tools/sprites.py`, Pillow via uv) turns every grid into
   an indexed PNG (sprite sheet: frames left to right) in the game's `art/`.
4. **Lint** in the same script, failing the build on: a character not in the
   palette, ragged rows, frame size mismatch, partial alpha in any PNG under
   `art/` (also hand-edited ones), colours outside the palette.
5. **Contact sheet** — every sprite at 8x nearest, on a checkerboard, with a
   1 px grid overlay and its name, under ~2000 px wide. This is what the model
   looks at to critique silhouettes and consistency; it is not what proves
   correctness (the lint does).
6. **Hand touch-ups** in Pixelorama or Aseprite are allowed on the PNG only
   if the grid is updated too (or the sprite is marked as PNG-sourced); the
   lint still runs.

Better than hand-writing every grid: have the model write **generators** —
recolour a base sprite per player, mirror, derive animation frames — whose
output still goes through the renderer and lint.

## Palettes

- **Sweetie 16** — soft and warm; the default for games for small children.
- **PICO-8 16** — high contrast, iconic.
- **Endesga 32** — warm and saturated, when 16 is not enough shades.
- Endesga 64, DB32 for bigger projects.
All on [lospec.com/palette-list](https://lospec.com/palette-list).

## Rules for clean pixel art

- Author at native resolution; never downscale.
- One grid size per sprite family (16x16 characters and tiles at 320x180).
- Characters read by silhouette and colour first: check the contact sheet at
  1x and in silhouette (solid fill) too.
- Outline or not, but consistently per game.
- Distinct colour per player seat so kids know which one is theirs.

## Sound (the same idea)

No native audio output either: sound effects are generated by our code
(sfxr-style parameters or a small Python synth writing WAV) and committed
with their parameter files. Check levels by measuring, not by ear.
